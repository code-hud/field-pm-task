# trading-api

Express API for the Heads Up Financial demo: sessions, portfolios, and a simulated
market, all stored in Postgres. The database is this service's private store — no
other service connects to it.

It has one outbound dependency, and it is optional: the
[fraud service](../fraud-service/), called on the way into every fill. With
`FRAUD_SERVICE_URL` empty the API screens nothing and behaves exactly as it did before
that service existed, which is how the tests and CI run.

The universe is the real S&P 500 ticker symbols, company names and GICS sectors;
every price, volume and fundamental is generated by `src/market/simulation.js` from
`MARKET_SEED`. See the root README's *How the data is made* for the model and for
why the fiction is stated as loudly as it is.

```bash
npm install
npm run seed           # migrate + populate (safe to re-run)
npm run dev            # :4000, reloads on change
npm test               # 190 tests, against a throwaway database

npm run seed -- --reset          # start over
npm run seed -- --help           # every flag
```

Needs a Postgres. From the repo root, `make db-up` starts one in Docker and
`make seed` populates it; `DATABASE_URL` points the API anywhere else.

```bash
docker build -t fpd/trading-api:dev .
docker run --rm -p 4000:4000 \
  -e JWT_SECRET=change-me \
  -e DATABASE_URL=postgres://headsup:headsup@host.docker.internal:5432/headsup \
  fpd/trading-api:dev
```

On boot the container waits for the database, applies pending migrations, and
seeds a market if the database is empty — so a clean volume produces a working
demo with no extra step. Both behaviours are switchable
(`DB_MIGRATE_ON_BOOT`, `DB_SEED_ON_BOOT`) for deployments that migrate separately.

## Layout

| Path | |
|---|---|
| `src/server.js` | listener + graceful shutdown |
| `src/app.js` | middleware and route mounting |
| `src/observability/` | OpenTelemetry helpers the app calls by hand — span attributes, failures, custom spans |
| `src/config/` | environment parsing, all defaults in one place |
| `src/auth/` | login policy (any username, non-blank password) and JWTs |
| `src/db/` | pool, migrations, and the seed script |
| `src/market/` | pure simulation (`simulation.js`), the writer loop (`ticker.js`), reads (`repository.js`), session clock (`clock.js`) |
| `src/portfolio/` | generation (`generator.js`) and SQL reads (`portfolioService.js`) |
| `src/orders/` | market order entry — fills into `orders`, `trades`, `lots`, `lot_closures`, and `accounts.cash` |
| `src/fraud/` | the call to the fraud service, and what an unanswerable check means |
| `src/accounts/` | find-or-create on first sign-in |
| `src/data/instruments.js` | the universe: real S&P 500 tickers, invented numbers |
| `src/data/sp500-constituents.csv` | the committed constituent list — provenance in `instruments.js` |
| `src/lib/random.js` | seeded PRNG — the data layer never calls `Math.random` |

Set the `OTEL_EXPORTER_OTLP_*` variables (see the root README) to report traces + metrics to SigNoz; with no
key the API logs one line at boot and runs exactly as it did before, which is how the
tests and CI run it. See *Runtime observability* in the root README for what is
covered and why this service is CommonJS.

**Charts are the one market read that can be revalidated.** Quotes are repriced every
two seconds, so `/api/market/instruments` is a different answer every time it is asked.
Bars are not: `daily_bars` is the seeder's and is never written again, and `intraday_bars`
is only touched during the regular session, and then only for the minute in progress. So
`GET /api/market/instruments/:symbol/history` carries an `ETag` built from the newest bar
and answers a matching `If-None-Match` with a `304` — for 5D through 1Y always, and for 1D
outside 09:30–16:00 ET. `Cache-Control: private, no-cache` rather than a lifetime, because
`--reset` rewrites the whole calendar underneath a client that was told it could stop
asking. The precondition is evaluated even when the request also carries
`Cache-Control: no-cache`, which `fetch()` adds by itself as soon as a caller sets
`If-None-Match` by hand; that directive is addressed to the caches in between, and this is
the origin.

**The order and the trade are different records.** `trades` is history: append-only, never
updated, and what the equity curve and the ledger read. `orders` is a lifecycle record — a
row is expected to change as the order resolves. Today they describe the same event, since
a market order is accepted and filled in one transaction; the split exists because an order
that has not filled yet is a real thing an account owns, and nothing about its lifecycle
should be able to rewrite what the account was worth on a past session. One order, one
trade: this venue has no partial fills, and the constraints say so rather than quietly
permitting a half-recorded one.

**A limit order names a price and waits.** If the market is already there it fills
immediately (`201`); otherwise it rests (`202`, status `OPEN`) until the tape reaches it.
Either way it fills at the *market*, not at the limit — a buy limit at 50 against a market
at 47 fills at 47 and the customer keeps the difference. The marketability test runs inside
the fill's transaction against the same quote row the fill uses: a check made a statement
earlier is a check against a price that has since moved, and losing that race means filling
above a limit. `007_limit_orders.sql` duplicates the test as a constraint, because the fill
path is where the bug would be.

**A resting order holds capacity.** A buy reserves `quantity × limitPrice` — the worst it
can cost — and a sell reserves the shares. That is what makes an accepted order stay
fillable: the money set aside when it was accepted is always enough when the tape arrives.
Reservations are derived from the open orders themselves, never stored on the account, so
there is no second number to drift; `/api/portfolio` reports `reservedCash` and
`availableCash` beside the balance.

**A client can retry an order without placing it twice.** Send an `Idempotency-Key` header;
the account's second use of that key answers **200** with the order it placed the first time,
rather than placing a second one. 200 rather than repeating the original code, for the same reason
202 exists — the caller asked "did this happen", and "yes, earlier" is not what 201 says.

The awkward part is the concurrent case. The unique index is on `(account_id, client_order_id)`,
and it raises `23505` on the *orders* insert — which happens after the lots, the closures, the
trade and the cash movement, with the account row lock held throughout. So the loser of a race has
done the entire fill before it finds out, and what makes replaying safe is that all of it is rolled
back. `23505` is deliberately not in the pool's retryable codes: retrying a duplicate key three
times reaches the same answer three times.

**Only `FILLED` and `OPEN` claim a key.** A rejection does not, so a client retrying after a
transient 503 can still get its order placed — a key burned by a refusal the caller never saw
would turn a retryable failure into a permanent one. The cost is that a client hammering an
unaffordable order is screened afresh each time, which is the right answer to a genuinely new
attempt.

The replay body is thinner than the original receipt on purpose. `priceImprovement`, the post-fill
position and `cashBefore` are computed during the fill and never stored, so they cannot be
reconstructed as they were *then* — only as they are now, which would be different facts wearing
the same field names.

A retry that gets as far as screening reuses the same fraud check key, derived from the client's,
so the fraud service counts it as one check. That only works because the screening ledger exists;
without it the retry would put a second observation in the account's velocity window.

**A resting order can be withdrawn** with `DELETE /api/orders/:id`, and it is one
conditional `UPDATE` rather than a read followed by a write. The sweep is filling orders on
every tick, so between reading a row and updating it the order can already have traded — and
a cancel that overwrote a fill would erase a trade that really happened while leaving the
cash movement and the lot behind. Putting `status = 'OPEN'` in the `WHERE` clause lets the
database decide which arrived first; the loser gets a 409. Nothing is unwound, because
nothing was stored: an order leaving `OPEN` releases its reservation by no longer being
counted.

There is no expiry. Every order is good until cancelled, so one placed far from the market
waits indefinitely and holds its capacity while it does.

**The sweep runs on the market tick**, on the replica that already holds the writer lock.
Both halves of that matter: it has to run after the new quotes are visible or it matches
against the prices it just replaced, and there has to be exactly one sweeper or one
instruction gets filled twice. A failure there is logged and dropped — a tape that stopped
repricing because an order could not fill would turn a contained problem into the visible
one.

"Exactly one sweeper" is an argument about replicas, and it left a hole inside a single
one: `setInterval` does not wait for its callback, so a tick that overran the interval ran
alongside the next. `day_high` and `volume` are read-modify-write, and two ticks that both
read before either wrote could send the day high backwards. A firing that finds the
previous tick still running is now skipped and counted — `skippedTicks` on
`/api/market/status`, because a writer outgrowing its interval is invisible otherwise. The
leader probe still runs on a skipped firing: a tick that overruns is exactly when this
replica is most likely to have lost its lock and least likely to notice.

**The sweep is bounded and resumable, and that changes what it promises.** It used to
shortlist the first 200 marketable orders every tick, which reads as strict global time
priority and is not — past 200 the tail was never looked at at all, and an order that
failed stayed at the head of the list occupying a slot on every subsequent tick. The
second of those is permanent starvation.

Each pass now has a wall-clock budget of a fraction of the tick, and returns a keyset
cursor the next pass resumes from; reaching the end of the book returns null, which starts
the next pass at the head. The cursor advances past failures too, which is the point. So
the promise is **time priority within a pass, with bounded staleness across passes**: an
order that becomes marketable mid-pass and sorts before the cursor waits for the wrap.
Weaker on paper, stronger in practice, because it is kept — every open order is reached
within one traversal, however long the book is and however many of its members are
failing.

Too much precision on a limit price is refused, not rounded: rounding 41.33335 up to
41.3334 for a buy raises the price the customer authorised, on the one number they were
explicit about.

**A refused order is recorded too**, with the code and the sentence explaining it —
including a fraud denial, which is the refusal someone is most likely to come looking for.
That record has to be written *outside* the fill's transaction, because the refusal is the
rollback: a row inserted inside it would be discarded along with the reason it exists. Two
rules follow. It never masks the original error — a bookkeeping failure turning
"insufficient cash" into a 500 would be the worse bug — and it files real orders only. A
400 means the request was never a well-formed order, and an unknown symbol has nothing for
the foreign key to reach.

**What a sale closed** is recorded, not just what it made. `trades.realized_pnl` says a
sale gained $412.60; `lot_closures` says which purchases it sold, what each cost, and when
they were bought — one row per lot the FIFO loop consumed, written in the fill's own
transaction. That cannot be reconstructed afterwards: `lots.closed_quantity` is a running
total, so once it moves, the order the shares went out in is gone. Sales made before the
table existed have no rows and never will, which is why anything reporting from it has to
say how much realized P/L it could not attribute. `004_lot_closures.sql` has the argument.

**Short and long term** on `/api/portfolio/realized` is a holding period, not tax advice.
It applies the one-year test to the lot's own dates — as an interval, so the calendar
decides which Februaries had 29 days — and stops there. Real lot accounting also has wash
sales, corporate actions, gifted and inherited basis, and elections that override the
calendar entirely, none of which this demo models.

**Fraud screening** happens before the transaction, never inside it: a fill holds a row
lock on the account, and an HTTP call under that lock would put another service's latency
inside a database transaction. A denial becomes a 422 (`fraud_rejected`) carrying the
reasons, and nothing is written. A check that cannot be made at all — unreachable, timed
out, or unreadable — is not a denial: the API fails open by default, filling the order and
reporting the skipped check both in the log and on the span. `FRAUD_FAIL_OPEN=false` inverts
that to a 503. The argument for the default is in `src/fraud/fraudClient.js`.

Environment variables are documented in `../../.env.example`. Probes: `GET /health`
(liveness — deliberately does not touch the database, so a blip cannot get the
container killed) and `GET /ready` (readiness — database reachable and seeded; also
reports whether this replica holds the market writer lock).
